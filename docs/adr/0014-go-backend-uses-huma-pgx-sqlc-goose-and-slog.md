# The Go backend uses huma, pgx with sqlc, goose and slog

`backend: go` has to meet the stack interface (ADR 0004) the way `backend: ts` does, and the author doesn't read Go, so its code has to stay small, close to the standard library, and easy for weaker coding models to extend by copying what's there. A prototype on 2026-11-10 proved this set together on Go 1.27.4. [The research note](../research/backend-go-prototype.md) has the comparison, the versions and the evidence.

- **HTTP and OpenAPI.** The standard library's `net/http` server and `http.ServeMux`, with huma v2 (`github.com/danielgtaylor/huma/v2`) through its `humago` adapter. Each route is one `huma.Register` call with typed input and output structs, and that call both serves the route and adds it to the OpenAPI 3.1 document. A small `cmd/openapi` command writes the document to `openapi.json` without starting a server, so the served routes and the exported file come from one definition, as they do with `@hono/zod-openapi`. orval generates the frontend's client from it.
- **Database.** pgx v5 (`github.com/jackc/pgx/v5`), with one `pgxpool` pool created at startup. Queries are written in SQL. sqlc reads the migrations as the schema, checks each query against it, and generates a typed Go function per query. sqlc is a binary pinned in mise, and its generated code imports only pgx.
- **Migrations.** goose v3 (`github.com/pressly/goose/v3`) as a library, inside a small `cmd/migrate` command in the backend's own module. The SQL files sit in `migrations/` beside a `migrations.go` that embeds them with `//go:embed *.sql`, so `bin/migrate` carries every migration and runs with no SQL files beside it. `mise run migrate` runs `migrate up` and `mise run migrate-new <name>` runs `migrate new <name>`. The build produces `bin/migrate` beside `bin/backend`, so the migration step can run from the backend's own image. The backend never migrates at startup.
- **Logger.** The standard library's `log/slog` with its JSON handler, wrapped in a handler that adds `trace_id` and `span_id` from the context. golangci-lint's `sloglint` with `context: all` makes every log call pass a context.
- **OpenTelemetry.** The Go SDK with the OTLP/HTTP trace and metric exporters, set up only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and `otelhttp` wrapping the `ServeMux`, with a filter that drops `/healthz` and `/readyz`.

## Considered options

- **oapi-codegen, spec-first.** It passed in the prototype and prevents drift by generating the server from the document. It was rejected because a model would write OpenAPI JSON by hand for every route, and every change regenerates hundreds of lines of Go that nobody reviews by eye. It's the fallback if huma stops being maintained, because it accepts the document huma exports.
- **swaggo/swag.** It was rejected because its comments aren't checked against the code, so the document can drift.
- **chi, echo or gin as the router.** They were rejected because, since Go 1.22, `http.ServeMux` matches methods and path parameters, which is all the template needs. echo and gin would also add a second handler style. huma has adapters for all three if that changes.
- **pgx without sqlc.** It needs no extra tool, but a wrong column name or a `Scan` in the wrong order only fails at runtime. sqlc catches both when it generates.
- **GORM.** It was rejected because its query builder hides the SQL from the author. Its `AutoMigrate` only runs when the code calls it, so GORM doesn't force migrating at startup.
- **The goose CLI as a `go tool`.** It was rejected because it adds 51 modules to the backend's `go.mod`, including drivers for five other databases.
- **dbmate.** It worked in the prototype and reads `DATABASE_URL` on its own. It was rejected because the image would need a second binary downloaded beside the backend, while `cmd/migrate` is built from the same `go.mod` and bumped by the same Renovate PRs.
- **golang-migrate.** It was rejected because each migration is two files, and a failed migration leaves the database marked dirty until someone runs `force`.
- **The `otelslog` bridge, zap or zerolog.** They were rejected because the bridge sends logs to an OTLP exporter rather than stdout, and zap and zerolog would add a module to write the JSON lines slog already writes.

## Consequences

- The backend's `go.mod` requires huma, pgx, goose and seven OpenTelemetry modules directly. Go modules pin exact versions, so no range rule applies (ADR 0007).
- Every route must go through `huma.Register`. A route added straight to the `ServeMux` is served and missing from `openapi.json`, so the generated `AGENTS.md` says this, and the freshness check can't catch it.
- huma's default config needs three settings turned off: the `$schema` field it adds to response bodies, the `/docs` page and the `/schemas` routes. Operation IDs are set to names like `getHealthz`, so orval's hook names match the ones the `backend: ts` document gives.
- huma documents error responses as `application/problem+json` with an `ErrorModel` schema, so a Go backend's `openapi.json` is longer than a TypeScript one and its error bodies differ. The frontend's orval config must set `override.fetch.forceSuccessResponse: true`, as the frontend template from #60 does. Without it, orval types the response data as the status body or `ErrorModel`, and the starter page's status line fails to type-check against the Go document.
- huma has one main maintainer. If it stops, oapi-codegen can generate a server from the last exported `openapi.json`. The `ServeMux`, the server and the middleware around it (`otelhttp` and the request logger) carry over. Each handler is a huma function, `func(context.Context, *Input) (*Output, error)`, that huma's adapter turns into the HTTP handler, so every handler would be rewritten against the interface oapi-codegen generates.
- `bin/migrate` embeds the migrations, so the migration step needs only that binary in its image. `//go:embed *.sql` fails the build when `migrations/` has no SQL file, so the template ships at least one migration. #107 and the author's Dockerfile should know both.
- sqlc fails when it has no query to generate, so the database starter needs a table and a query, or it adds sqlc only when the first query arrives. #107 decides which. sqlc's generated code gets a freshness check like `openapi.json`'s.
- The final image is a static binary on a distroless base. The prototype ran `CGO_ENABLED=0` builds of both binaries on `gcr.io/distroless/static-debian13:nonroot`. The Dockerfile and CI jobs stay the author's.
